# ADR-0023: Tool 返回结果大小 — 配置阈值 + 超限 LLM 压缩

## 状态
已接受

## 背景
企业 API 返回可能巨大(列表 API 返回 10MB+ JSON)。直接塞进 LLM 上下文会爆 token 预算、抬高成本、淹没信号。需要卫生化处理。

## 决策
Tool 可配置 `max_response_size`(默认 8KB)。超限后的处理:

**处理顺序**:先经 ADR-0022 的注入检测(对原始 Tool 返回做检测),通过后再做大小判断与压缩。

1. **未超限** — 原始结果直接进 LLM 上下文。
2. **超限** — 后端调用 Langfuse 上的 `result-summarizer` Prompt,基于原结果生成面向当前 Planner 上下文的压缩版本(保留关键信息、丢弃冗余)。
3. **原始结果** — 无论是否压缩,都存 MongoDB(供审计 / 业务人员后续查询);Planner 拿到的是压缩版本。
4. **极端超限** — 压缩后仍超 8KB,继续二次压缩,直到达标或达到压缩轮次上限(默认 2 轮)。

## 后果
- LLM 上下文大小可控,成本可预测。
- 业务人员需要原始细节时,可通过 Tool 的"原始数据查看"入口或 Plan 详情看到完整结果。
- 后端需要实现"原始结果 + 压缩版本"双存储。
- `result-summarizer` Prompt 是关键资产,放在 Langfuse 上可调优。
- 多次压缩有成本,极端大数据场景需要分页(单独跟进)。
